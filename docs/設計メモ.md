# 実装設計メモ(初期計画.md の補足)

`docs/初期計画.md` を実装に落とすにあたって、仕様のままだと壊れる/曖昧な箇所を詰めた決定事項。
実装はこのメモの決定を優先する。

## D1. スケジューラの「幽霊発火」対策 — `roundId`

`startGame` は `beginPlaying`(3秒後)と `endGame`(63秒後)を `ctx.scheduler.runAt` で予約する。
ここで、ホストがゲーム中に「リセット」した場合、予約済みの `endGame` は生き残っていて、
ロビーに戻ったはずの部屋を 63 秒後に `finished` に飛ばしてしまう。

対策として `rooms.roundId: number`(初期値0)を持つ。

- `startGame`: `roundId = room.roundId + 1` に更新し、スケジュール時の引数に `roundId` を渡す
- `resetRoom`: `roundId` をさらに +1 する(予約済みジョブを無効化)
- `beginPlaying` / `endGame`: `room.roundId !== args.roundId` なら**何もせず return**

`ctx.scheduler.cancel` を使う手もあるが、id の保存・失効管理が増えるだけなので世代番号方式を採る。

## D2. `paint` は失敗時に throw しない

クールダウン違反・時間外タップは**例外ではなく `{ ok: false, reason }` を返す**。
理由: 楽観的更新(`withOptimisticUpdate`)は mutation が reject されるとロールバックするが、
throw するとクライアント側にエラーが伝播しコンソールが赤くなる。連打は「起こって当たり前」の
正常系なので、静かにロールバックさせる。

不正リクエスト(部屋が無い、座標が範囲外など、UIからは起き得ないもの)のみ throw する。

## D3. `players` に `by_room_and_player` インデックスを追加

`paint` は毎タップで「この部屋のこのプレイヤー」を引く。`by_room` で全員取ってから filter だと
毎回6件読むことになるので、`["roomId", "playerId"]` の複合インデックスで1件引きにする。
(発表ネタ的にも「インデックスを張る/張らない」の差を見せやすい)

## D4. `getCells` は射影して返す

ドキュメントそのまま(`_id` / `_creationTime` 込み)ではなく `{ x, y, color }` の配列を返す。

- 転送量が減る(セルは毎タップ再送される)
- 楽観的更新でクライアントが「まだ存在しないセル」を足すときに、偽の `_id` を捏造しなくて済む

`.collect()` ではなく `.take(MAX_GRID_CELLS)` で上限を明示する。

## D5. `paint` の色はサーバーが決める

`paint` の引数に色は含めない。サーバーが `players.color` を読んで塗る(他人の色で塗る改竄を防ぐ)。
楽観的更新側は、コンポーネントが持っている自分の色をクロージャで捕まえて使う。

## D6. `joinRoom` は判別可能ユニオンを返す

`{ ok: true, roomId, playerDocId }` または `{ ok: false, reason: "notFound" | "full" | "inProgress" }`。
UI 側でメッセージを出し分けるため。ただし**同じ `playerId` の再入室(リロード/再接続)は
`status` に関係なく `ok: true`** とする(ゲーム中のリロードで締め出されないように)。

## D7. 認証なしの割り切り

`playerId` はクライアント生成・自己申告なので、理屈の上ではホストのなりすましが可能。
イベント用デモとして許容する(Convex の guidelines が言う「userId を引数で受けるな」は
本来正しいが、ここは認証レイヤ自体が存在しない前提の仕様)。本番運用するなら Convex Auth を入れて
`ctx.auth.getUserIdentity()` に置き換えるポイント、として発表で触れられる。

## D8. 定数は `convex/constants.ts` に集約

パレット6色・グリッドサイズ・クールダウン・カウントダウン秒数・ラウンド秒数をここに置き、
フロントエンドからも `import { PALETTE } from "@/convex/constants"` で参照する(型・定数の一元管理)。

## D9. グリッドの列数はインラインstyleで

`gridSize` は DB 由来の動的な値なので、Tailwind のクラス名(`grid-cols-20`)ではなく
`style={{ gridTemplateColumns: \`repeat(${size}, minmax(0, 1fr))\` }}` を使う。

## D10. 残り時間はクライアント計算

`startsAt` / `endsAt` から `setInterval(100ms)` で算出。サーバーには問い合わせない。
クエリ内で `Date.now()` を読まない(Convex のクエリは時間経過では再実行されないため)。

## D11. クールダウンは `cooldowns` テーブルに分離

当初は `players.lastPaintedAt` にクールダウン時刻を持たせる想定だったが、これは Convex の
**「高頻度更新データを安定データと同じドキュメントに置くな」** というアンチパターンに正面から当たる。

Convex のクエリ無効化は**ドキュメント単位**。`getRoom` は `players` を読んでいるので、
`paint` が毎タップ `players` を patch すると、**タップのたびに全員の `getRoom` が再実行され、
プレイヤー一覧が6端末に再送される**。6人が300ms間隔で叩けば毎秒20回。完全な無駄。

そこで `cooldowns(roomId, playerId, lastPaintedAt)` を別テーブルに切り出した。
`paint` が触るのは `cells` と `cooldowns` だけになり、`getRoom` の購読は
**ステータス変化とプレイヤーの増減・色変更のときだけ**流れる。

発表ネタとしても「無効化の粒度=ドキュメント」という Convex の肝を説明しやすい。
