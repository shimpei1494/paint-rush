Convex × Vercel デプロイの仕組み

Paint Rush は main にマージするだけで本番へ、ブランチを push するだけでプレビューへ反映される。 その「よしなに動く」部分で実際に何が起きているのかを分解した資料。
設定の手順そのものは デプロイ手順.md を参照。

1登場人物 — 1プロジェクトに複数のバックエンド

前提として、Convex の「デプロイメント」は実際に動いているバックエンドの実体そのものである。 関数・スキーマ・データベースが一式入った箱が、1つのプロジェクトの中に用途別に複数存在する。 これを Vercel 側の環境（Production / Preview）と対応させるのが基本形になる。

ポイント

3つはデータベースも完全に別物。プレビューで部屋を作っても本番の部屋には出てこないし、 ローカルで壊れたデータを作っても本番には影響しない。この分離が「安心して壊せる」土台になっている。

開発デプロイメントは人間専用ではない

開発デプロイメントは「メンバー1人につき1つ」が基本形だが、それはローカルPCに限った話ではない。 Claude Code のようなクラウド上のコーディングエージェントにも、自分のPC用とは別の専用devデプロイメントを割り当てられる。 エージェントはブラウザログインができないため専用の認証キーを発行して繋ぐ形になり、 自分の作業中のデータやスキーマとエージェントの変更がぶつからないよう分離できる。

23つの環境変数 — 誰が書いて、何を決めるのか

仕組みの大半は、次の3つの環境変数の役割分担で説明できる。混乱しやすいのは CONVEX_DEPLOYMENT と CONVEX_DEPLOY_KEY が名前は似ているのに使われる場面が正反対である点。

変数 どこに存在するか 誰が書くか 何を決めるか
CONVEX_DEPLOYMENT ローカルの .env.local（Git 管理外） convex dev が初回に自動生成 ローカル開発の接続先。自分専用の開発デプロイメント名が入る
CONVEX_DEPLOY_KEY Vercel の環境変数（ローカルには置かない） 人間が Convex ダッシュボードで発行して登録 CI からの接続先と書き込み権限。どのデプロイメントに関数を push してよいかを表す認証情報
NEXT_PUBLIC_CONVEX_URL ローカルは .env.local / ビルド時はメモリ上 ローカルは convex dev、CI は convex deploy が自動注入 ブラウザ側の接続先。React が購読を張りにいく URL
ここが効いている

NEXT_PUBLIC_CONVEX_URL を手で管理しなくていいのが、この構成の一番大きな恩恵。 ローカルでも Vercel でも「今デプロイした先の URL」がビルドコマンドに自動で渡されるので、 フロントの接続先とバックエンドの実体がズレようがない。

3ローカル — npm run dev の中身

package.json の dev スクリプトは、2つのプロセスを1コマンドにまとめたもの。

"dev": "convex dev --start 'next dev'"

convex dev はローカルのファイルシステムを監視し続ける常駐プロセスで、 --start に渡したコマンド（ここでは next dev）を同時に起動する。 convex/ 配下を保存すると、次のループが回る。

型の再生成が同じループに入っているのが効いている。 convex/game.ts に endRoundByHost を追加したとき、保存した直後からフロント側で api.game.endRoundByHost が補完され引数の型も効くようになったのはこれが理由。 バックエンドとフロントエンドの間に手書きの型定義や API クライアントが挟まっていないので、ズレが原理的に発生しない。

4Vercel — npx convex deploy --cmd 'npm run build' の中身

Vercel の Build Command はデフォルトの next build ではなく、これに差し替えてある。 Convex のデプロイが親、Next.js のビルドが子という入れ子構造になっているのが最大のポイント。

  1. 接続先を決める CONVEX_DEPLOY_KEY を読み、どのデプロイメントに向けるかを決定する。CI ではこれが優先され、無ければ CONVEX_DEPLOYMENT にフォールバックする。
  2. ビルド環境とキーの種類が合っているか検証する Vercel が渡す VERCEL_ENV（production / preview）と、キーの種類が対応しているかを確認する。不一致ならここでビルドを中止する（→ 第6章）。
  3. プレビューの場合はデプロイメントを用意する Preview キーだった場合、Git ブランチ名に対応したデプロイメントを新規作成する。同名のものが既にあればそれを再利用し、データも保持される。
  4. Convex 関数を型チェックしてバンドルする convex/ 配下を typecheck し、convex/_generated を再生成したうえで、依存ごとバンドルする。
  5. 関数・インデックス・スキーマを push する 対象デプロイメントにバックエンドが反映される。フロントのビルドより先にここが完了する。
  6. --cmd のコマンドを実行する デプロイ先の URL を NEXT_PUBLIC_CONVEX_URL として環境に注入した状態で npm run build を走らせる。変数名はフレームワークの規約から自動判別される（--cmd-url-env-var-name で明示指定も可能）。
  7. ビルド成果物が完成する 正しい接続先が焼き込まれた Next.js の成果物を Vercel が配信する。
なぜこの順序なのか

バックエンドが先、フロントエンドが後という順序に意味がある。 フロントがビルドされて公開される時点で、それが呼ぶ Convex 関数はすでに存在していることが保証される。 逆順だと「新しい画面が、まだ存在しない関数を呼ぶ」瞬間が生まれてしまう。

さらに npm run build は tsc --noEmit && next build なので、フロント側の型エラーがあればここで落ちる。 つまり「バックエンドは通ったがフロントが壊れている」状態はビルド失敗として検出される。

5CONVEX_DEPLOY_KEY の正体と振り分け

CONVEX_DEPLOY_KEY は「どのデプロイメントに、どの権限で書き込んでよいか」を1本の文字列に封じ込めた認証情報。 Paint Rush では権限を deployment:deploy だけに絞ってあり、関数をデプロイする以外のことはできない。

重要なのは、Vercel 上ではCONVEX_DEPLOY_KEY という同じ名前の変数が2本登録されていること。 Vercel は環境スコープごとに別の値を持てるので、ビルドが走る環境に応じて片方だけが注入される。

6実際に遭遇したエラーの読み方

Preview 用のキーを設定する前、feature/deploy ブランチのプレビュービルドが次のエラーで落ちた。

✖ Detected a non-production build environment and "CONVEX_DEPLOY_KEY"
  for a production Convex deployment. This is probably unintentional.

これは第4章のステップ2で止まった状態。VERCEL_ENV=preview なのに Production Deploy Key が渡されていたので、 Convex が「意図しない設定だろう」と判断してビルドを中止した。

この安全装置が無かったら

feature/* ブランチを push するたびに、まだレビューもマージもしていない関数が本番の Convex に反映されてしまう。 フロントはプレビューURLに閉じているのにバックエンドだけ本番が書き換わる、という最悪の組み合わせになる。 エラーで止まったのは正しい挙動だった。

同じ理由で、プレビューのフロントだけを本番バックエンドに向ける運用も勧められない。 ブランチで変更した Convex 関数がデプロイされないまま新しいフロントが動くことになり、 たとえば endRoundByHost を追加したブランチのプレビュー画面で「ゲームを終了」を押すと、 本番に存在しない関数を呼んで実行時エラーになる。スキーマを変えていればもっと分かりにくい壊れ方をする。

73つの経路まとめ

ローカル プレビュー 本番
きっかけ ファイルを保存 main 以外のブランチを push main にマージ
実行コマンド convex dev --start 'next dev' npx convex deploy --cmd 'npm run build'（Vercel の Build Command。両者で同一）
接続先の決定 CONVEX_DEPLOYMENT（.env.local） Preview スコープの CONVEX_DEPLOY_KEY Production スコープの CONVEX_DEPLOY_KEY
フロントの接続先 NEXT_PUBLIC_CONVEX_URL（いずれも自動で設定される。手で書く必要はない）
データ 自分専用。壊しても影響なし 空から始まる。ブランチ内では保持される 実ユーザーのデータ
寿命 消えない 5日で自動削除（無料プラン） 消えない
型の再生成 保存のたびに自動 ビルド中に自動（convex/_generated の状態に依存しない）

8まとめ — 何が開発体験を良くしているのか

1. 接続先の管理が消えている。 NEXT_PUBLIC_CONVEX_URL を人間が管理しないので、「URL を書き換え忘れて別の環境を見ていた」類の事故が起きない。

2. バックエンドとフロントの型が同じループで生成される。 API クライアントを手書きしないため、関数を追加した瞬間にフロントで補完され、消せばフロントが型エラーになる。

3. デプロイの順序が固定されている。 「バックエンド → フロント」の順が --cmd の入れ子構造で強制されるので、順序ミスによる不整合が起きない。

4. 環境の取り違えを検知して止まる。 キーの種類とビルド環境の突き合わせが自動で行われ、危険な組み合わせはビルドエラーになる。
